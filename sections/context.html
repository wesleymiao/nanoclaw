What NanoClaw is, today

NanoClaw runs one disposable Docker container per chat group/conversation. A Channel Router polls a chat platform (currently Feishu/Lark), maps each chat ID to a group folder, and hands work to a per-group Queue (max 5 active containers at once, independent ordering). A Session Manager persists each group's Claude session UUID in local SQLite so a follow-up message resumes the same Claude conversation. The Container Runner builds mounts/args and launches the container with a 30-minute idle timeout. All of this — Docker daemon, SQLite, workspace disk, credential stores — lives on a single VM.

The problem this document is about

The single-VM model has a ceiling: everything (routing state, session registry, workspaces, transcripts) is local to one host, and only one chat platform is wired up. Two pressures follow from that — scale (one VM eventually runs out of CPU/RAM/container slots as tenants and groups grow) and multi-tenancy/multi-channel (adding Web, WeCom, Slack, etc. means the "one chat ID → one group" assumption baked into today's code needs to generalize). This document works through a design that solves both, plus a concrete, de-risked path to get there and a way to make that path testable without depending on live cloud infrastructure at every step.

How the document is organized

Chapter 1 — Current Single-VM Architecture documents NanoClaw exactly as it runs today: the core request flow, how credentials/auth work, the session lifecycle and its 30-minute idle window, how the container image is built and shared, what "scaling" means today (per-group container concurrency, not multi-VM), and the full credential matrix. Read this first if you're unfamiliar with the current system.

Chapter 2 — Test Harnesses is the philosophy this whole effort is built on: before undertaking the multi-VM rewrite, get the test harness right for what exists today — fast, local, deterministic, agent-friendly. It covers the current single-VM system's real Vitest harness (mocked Docker spawn, fake timers, in-memory SQLite) first, then generalizes the same tiered ladder to the future multi-VM design's networked dependencies.

Chapter 3 — Multi-Tenancy Multi-VM Design is the proposal: an interactive diagram-backed design plus three concrete walkthroughs (Feishu new conversation, Feishu follow-up, Web follow-up) showing exactly how a message gets routed to the right worker and picks up the right session every time; and a 9-stage incremental rollout plan (Stage 0–8) that externalizes one dependency at a time on a single VM before ever touching real multi-VM infrastructure.

Key vocabulary used throughout

Group — one conversation/chat, the unit of isolation (own workspace, own Claude session, own queue ordering). Session — a group's persisted Claude conversation UUID plus its live container/idle-timeout state. Lease — in the multi-VM design, the exclusive, renewable claim one worker holds on a group so no two workers process the same conversation concurrently. Worker — a VM (today: the single host) running the container runner and pulling from the queue. Channel — the ingress integration for a chat platform (Feishu today; Web and others proposed in Chapter 3).
