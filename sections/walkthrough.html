3.1 · Multi-tenancy Multi-VM Design with Walkthroughs

Proposed target multi-VM architecture — none of this is built yet. Today NanoClaw is single-VM only (in-process queue, local SQLite, local disk, one Docker daemon). Three scenarios below trace the same diagram end-to-end; numbers on each diagram correspond to the numbered list to its right. Click a box in any diagram for its rationale. Background reference material follows the three walkthroughs.

1. Feishu: brand-new conversation

Steps 1–9: brand-new Feishu conversation

  1. Feishu box — a user starts a brand-new conversation; the message arrives over the app's persistent WS connection, delivered to the one pinned Container Apps replica that owns that lease.
  2. Feishu box (its own ingress) — resolves (channel=feishu, tenant_id=app_id, conversation_id=chat_id) → a brand-new group (no prior entry exists yet), then publishes the event directly to the queue itself (does not process it, and there's no separate Ingress hop).
  3. Queue — event lands in the Service Bus session-enabled queue as a brand-new session, partitioned by tenant_id (the Feishu app).
  4. Registry — looked up for this conversation and found empty: no session UUID or worker lease exists yet.
  5. Any worker's long-poll — because this session is brand-new, whichever worker's blocking receive call returns first wins the race and accepts it, acquiring the registry lease and dequeuing the message. Accepting a session grants an exclusive lock, not just one message: this worker keeps its receive loop for that session open (renewing the lock) for as long as the container stays warm, so every later message in this conversation lands straight back on this same worker — see Walkthrough 2 for exactly how that follow-up path works.
  6. Container spin-up — that worker runs a fresh docker run for this brand-new group (there's nothing to reuse yet), consuming one of its 5 concurrency slots.
  7. Storage — the container creates the group's shared workspace, JSONL transcript, and IPC directory for the first time.
  8. Reply path (streamed, not one-shot) — a single turn is not one reply: Claude Code emits a running sequence of events — reasoning chunks, tool-call-started, tool-call-result, partial text — and agent-runner flushes each one to the group's IPC output directory as it happens. The worker doesn't know or care which of N Feishu-app replicas is running — it just publishes each event to a pub/sub channel keyed by conversation_id. Only the one Feishu-app replica that registered the WS lease for that conversation_id (in Azure Cache for Redis, at connection time) is subscribed to that exact channel, so only it receives the events and relays them, in order, to the pinned Feishu WS connection — no separate Ingress process is involved — the chat sees live "using tool X…" / "thinking…" updates before the final answer, not a single blocking wait.
  9. Idle teardown — after ~30 minutes idle with no follow-up, docker rm frees the slot and the worker explicitly completes/closes the Service Bus session, releasing the sticky lock from step 5 so a future message can go to any worker.

2. Feishu: follow-up message (existing conversation)

Steps 1–9: Feishu follow-up message

  1. Feishu box — the user sends a follow-up message in the SAME chat, delivered to the same pinned Container Apps replica that owns the WS lease.
  2. Feishu box (its own ingress) — resolves the same (channel=feishu, tenant_id=app_id, conversation_id=chat_id) key as the earlier message in this conversation and publishes to the queue.
  3. Queue — event lands in the SAME Service Bus session as before — a session that is still open and exclusively locked by the worker that has been handling this conversation.
  4. Registry — the lease entry already shows this conversation's owning worker from the earlier message, still within its TTL — no new lease is created.
  5. Same worker, sticky session lock — mechanically: back when this conversation started, Worker A called AcceptNextSessionAsync(), which returned a session receiver bound to this exact SessionId (= the group key) and told Service Bus to lock it server-side. Worker A has been looping ReceiveMessagesAsync() + RenewSessionLockAsync() on that receiver ever since — even through gaps with nothing to receive — which is what keeps the lock alive through the container's 30-minute idle window. Because the lock is still held, this new message (same SessionId) is simply the next item Worker A's already-running ReceiveMessagesAsync() call picks up — no new accept, no lookup. Any other worker calling AcceptNextSessionAsync() never even sees this session offered, since Service Bus filters out locked sessions before offering them — so unlike Walkthrough 1's brand-new conversation, there's no "whichever worker wins" race this time.
  6. Container reuse (no docker run) — the worker finds its existing container for this group still running and forwards the new prompt to it over IPC, passing the conversation's ongoing Claude session UUID — no new container, no new slot consumed.
  7. Storage — the container appends to the SAME shared workspace/transcript/IPC directory it was already using; nothing about the file layout changes.
  8. Reply path (streamed, not one-shot) — same as Walkthrough 1: the worker publishes each event to the pub/sub channel keyed by conversation_id; whichever Feishu-app replica holds the WS lease for that conversation relays the events, in order, back to the pinned WS connection.
  9. Idle timer resets, no teardown this cycle — because a new message arrived before the 30-minute idle timeout fired, both the container and the sticky session lock stay alive, extending the window; teardown (and lock release) only happens if this conversation later goes quiet for a full 30 minutes.

3. Web channel: follow-up message

Steps 1–9: Web channel follow-up message

  1. Web channel box — the same logged-in browser sends a follow-up message over its still-open JWT-authenticated socket, later in the same conversation.
  2. Web channel box (its own ingress) — validates the JWT, then resolves the same (channel=web, tenant_id=user_id, conversation_id) key as the earlier message in this conversation and publishes directly to the queue (no separate Ingress hop).
  3. Queue — lands in the SAME Service Bus session as before — a session that is still open and exclusively locked by the worker that has been handling this conversation.
  4. Registry — the lease entry already shows this conversation's owning worker from the earlier message, still within its TTL — no new lease is created.
  5. Same worker, sticky session lock — identical mechanism to Feishu's follow-up case (Walkthrough 2, step 5): the worker's receiver has held an exclusive Service Bus lock on this session since the conversation started, kept alive by looping ReceiveMessagesAsync() + RenewSessionLockAsync() even through idle gaps. This message is just the next item that already-open loop picks up — no other worker's AcceptNextSessionAsync() call is ever offered this session while the lock holds.
  6. Container reuse (no docker run) — the worker finds its existing container for this group still running and forwards the new prompt to it over IPC, passing the conversation's ongoing Claude session UUID — no new container, no new slot consumed.
  7. Storage — the container appends to the SAME shared workspace/transcript/IPC directory as before; nothing about the file layout changes.
  8. Reply path (streamed, not one-shot) — same live event stream as Feishu — reasoning chunks, tool-call-started/result, partial text — flushed to IPC as they happen. The worker publishes each event to the same pub/sub-by-conversation_id channel; the subscriber is whichever Web-app replica registered this user's socket id at connect time — there's no separate Ingress process here either. That replica alone receives and relays the events, letting the web UI keep rendering incremental "typing" / tool-use indicators.
  9. Idle timer resets, no teardown this cycle — because a new message arrived before the 30-minute idle timeout fired, both the container and the sticky session lock stay alive, extending the window; teardown (and lock release) only happens if this conversation later goes quiet for a full 30 minutes.

Reference: rationale and Azure mapping

Why single-VM hits a ceiling

Today's per-group queue lives in NanoClaw's own process memory, the session registry is a local SQLite file, group workspaces/transcripts/IPC live on the VM's disk, and there is exactly one Docker daemon and one copilot-api instance. None of that can be shared across a second VM without changes.

What moves out of the process

Three components get externalized: the queue (in-memory → Redis Streams/SQS/Service Bus), the session + lease registry (SQLite → Postgres/etcd), and durable storage (local disk → NFS/Azure Files/EFS mounted by every worker).

How does a later message in the same conversation reach the same worker (within the 30-min TTL)?

This is enforced by Azure Service Bus's session lock, not by anything the worker or registry has to decide explicitly. Mechanically: an idle worker calls AcceptNextSessionAsync() (or AcceptSessionAsync(id)), which returns a session receiver bound to one specific SessionId (= the group key) — and the instant that call succeeds, Service Bus marks that SessionId exclusively locked server-side. The worker then loops ReceiveMessagesAsync() + RenewSessionLockAsync() on that same receiver continuously — even through gaps with nothing to receive — for as long as that group's container stays warm; the renewal calls are what keep the lock alive across idle periods, not the act of receiving itself. Because locked sessions are filtered out of the pool before being offered to anyone, any other worker's AcceptNextSessionAsync() call never even sees this session — so every subsequent message published to that conversation_id, arriving anywhere inside the 30-minute idle window, is simply the next item Worker A's already-running ReceiveMessagesAsync() call picks up — no new accept, no lookup. Nothing needs to look up "which worker had this conversation last": the queue itself is the source of truth for that. The registry's worker-lease field is a mirror of this fact (useful for dashboards/debugging and for the reply-pub/sub validity check), not the mechanism that enforces it. There are exactly two ways the lock lets go: (1) the worker explicitly calls CloseAsync() on the receiver at idle-teardown, releasing the lock immediately so any worker may accept it next, resulting in a cold docker run; or (2) the worker crashes and stops renewing, so the lock's TTL simply expires, after which a different worker accepts the now-unlocked session, finds no container running, and starts one fresh — resuming from the last saved Claude session UUID and transcript on shared storage, so no conversation state is lost even on a mid-conversation worker failure.

Shared storage vs. single-VM: what actually changes

The directory shape is identical to today: one folder per group, containing the workspace files, the .claude JSONL transcript, and the IPC input/output directories — same paths, same file layout, same code in agent-runner and NanoClaw that reads/writes them. The only thing that changes is the backing volume that path resolves to: today it's the single VM's local disk, so only that one VM's Docker daemon and NanoClaw process can ever see it; in the multi-VM design it's an Azure Files/NetApp Files network mount mounted identically, at the identical path, by every worker VM. That's what makes the lease model work at all — when Worker 3 acquires a group's lease that Worker 1 handled an hour ago, it opens the exact same folder and sees the exact same transcript/workspace/IPC state, because "local disk" and "shared mount" are interchangeable from the application code's point of view. Nothing in agent-runner, the container, or the transcript/resume logic needs to know which VM it's running on.

IPC directories still needed — pub/sub sits downstream of them

Yes, IPC directories don't go away, and their job doesn't change: a container is a separate process (and now separate filesystem namespace) from the worker, so writing new chat input into the group's IPC input directory and reading streamed output (reasoning chunks, tool calls, partial text) from its IPC output directory is still how the worker and the container talk to each other at all — same as single-VM today. What's new in the multi-VM design is what happens after a worker reads an event out of the IPC output directory: instead of the single host process forwarding it straight to the one Feishu WS connection it also owns, the worker publishes that event to the pub/sub channel keyed by conversation_id, so whichever channel-app replica owns the actual socket (which may be running on a completely different machine than this worker) receives it. So the full chain is container → IPC output directory (shared mount) → worker reads it → worker publishes to pub/sub → channel app relays to the socket — IPC handles the container↔worker handoff, pub/sub handles the worker↔channel-app handoff across the network. Neither replaces the other; they solve different halves of the same problem.

Which Azure service implements the reply pub/sub? Redis, not Service Bus

It's Azure Cache for Redis's native PUBLISH/SUBSCRIBE commands — the same Redis instance already holding WS/socket-lease ownership records, not a second Service Bus. The two messaging needs are genuinely different shapes: the inbound queue needs durability and exactly-one-consumer, ordered-per-group delivery for chat messages that must never be dropped — that's what Service Bus sessions are built for. The reply fan-out needs the opposite: an ephemeral, fire-and-forget broadcast to whichever single replica currently holds a live socket for a given conversation_id, with channels created and torn down constantly as connections open/close — that's exactly Redis Pub/Sub's use case (the same pattern behind Socket.IO's and SignalR's Redis backplanes). Service Bus Topics could technically do fan-out too, but they're built for durable, pre-provisioned subscriptions, not millions of ad-hoc per-conversation channels — the wrong tool here. If the team later wants a fully managed alternative purpose-built for this exact "broadcast to whichever server owns this connection" problem, Azure Web PubSub is the dedicated PaaS option, but reusing Redis avoids adding a fourth stateful service to the design.

Group-to-worker leasing is the key invariant

Exactly one worker may hold the lease for a group at a time (TTL-based, renewed while the container runs). This preserves the same guarantee NanoClaw relies on today — a group's JSONL transcript is only ever written by one process — while allowing any worker to pick up any group.

Channel apps and copilot-api both scale independently (not pictured)

Feishu and Web are each already a stateless-ish, horizontally scaled Container Apps app in their own right (Feishu pinned per-app-replica for its WS lease, Web fully stateless) — there's no separate ingress tier to scale as a third thing. copilot-api becomes a small replicated cluster reading the GitHub token from a shared secret store instead of one host file — omitted from the diagram since it's a supporting service every worker calls, not part of the core request path being illustrated.

Concrete Azure mapping

Feishu & Web channel apps (each = its own ingress): Azure Container Apps behind Azure Front Door · Auth: Microsoft Entra External ID · Queue: Azure Service Bus (session-enabled) · Registry: Azure Cosmos DB (TTL leases) or Postgres Flexible Server · Workers: Azure VM Scale Sets — the one tier that stays IaaS, because Docker-in-Docker + Playwright/Chromium needs privileged, nested containers that Container Apps/AKS-without-privilege can't give it · copilot-api (not pictured): Azure Container Apps, secrets in Azure Key Vault · Storage: Azure Files Premium or Azure NetApp Files · WS/lease state + reply pub/sub: Azure Cache for Redis (key/value for lease ownership, native PUBLISH/SUBSCRIBE for the streamed reply fan-out — not Service Bus, which is reserved for the durable inbound work queue).

Failure handling

If a worker VM dies mid-run, its leases expire on TTL and any other worker can resume the affected groups from the shared session registry and shared storage — the same stale-session recovery path NanoClaw already has, extended across hosts instead of just across container restarts.

How a worker wakes up

No polling loop: each idle worker keeps a blocking receive call open against its Service Bus session queue, so the SDK call itself returns the instant a new message is available — the OS/network stack does the waiting, not a CPU spin. The worker then acquires the group's lease in the registry (so no other worker double-processes it) and dequeues the message in the same step.

How the system decides to add or remove VMs

Azure Monitor autoscale (or KEDA) watches one ratio — queue depth ÷ total pool container capacity (workers × 5 slots each) — as a custom metric on the Service Bus queue. Cross a high-water threshold for a sustained window (e.g. pool-wide slot utilization >90% for 2 minutes) and it adds VMSS instances; the new instance just needs to boot and start long-polling, so it's already receiving work within seconds. Scale-in is intentionally more cautious: an instance is only marked for removal once the registry shows it holds zero active leases (zero running containers), so autoscale never kills a VM mid-run — it waits for that worker to go idle first.

Two scaling layers, two speeds

Container-level (inside one VM): the instant a worker acquires a group's lease it runs docker run for that group — sub-second, purely local, no autoscaler involved — up to that VM's own concurrency limit (5 concurrent containers, matching today's single-VM limit). When a group goes idle, docker rm frees that slot for the next lease. VM-level (across the pool): the autoscaler never looks at one VM's slot count — it only reacts when most/all VMs are near their own limit at the same time, meaning the whole pool, not any one VM, is out of room. That's a slower, minutes-scale decision (boot a new VM) versus the container layer's sub-second one. Concretely: five simultaneous group requests to an idle worker never trigger autoscale (it just fills its own 5 slots); a sixth simultaneous request pool-wide, with every worker already full, is what actually adds a VM.

What stays the same

Per-group isolation (one folder, one session UUID, one IPC namespace), the container image and its trust boundaries, and the idle-timeout/cleanup lifecycle are unchanged — they just now apply per-worker instead of per-VM.

Multi-tenant sharding generalizes to one key

The fix for the single-Feishu-app rate-limit ceiling and the fix for adding a Web channel are the same change: generalize group identity to (channel_type, tenant_id, conversation_id) everywhere — each channel app's own routing resolution, queue partition key, and the lease registry's composite key. Feishu shards by app_id (many users share one bot's quota); Web shards by user_id (each login is already its own boundary). Workers, containers, and shared storage don't need to know the difference.

Web channel changes the ingress and trust story

Feishu's bottleneck is external and stateful (one leased WS connection per app serving many users). Web has no external quota, but needs a component NanoClaw doesn't have today: its own Auth/Identity Service, since Feishu supplies user identity for free and a browser login doesn't. Web also simplifies the container trust boundary — there's no external chat-platform credential to inject into a Web-originated container, since replies just flow back through IPC → the worker → pub/sub → straight to the Web app's own socket (no separate ingress hop in between).
