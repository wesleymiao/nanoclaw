2.1 · Testing Today's Single-VM System

Philosophy: harness-first, then architecture-first. Before any multi-VM externalization work starts, get the test harness right for what exists today — one VM, one Docker daemon, one SQLite file, an in-process queue. This is test-first development applied at the whole-system level, not just per-function: the payoff isn't "more tests," it's tests that are local (no cloud, no network), stable (deterministic, no flaky real-time waits), and agent-friendly (one command, fast enough to run after nearly every edit). Only once today's system has that kind of harness does it make sense to extend the same ladder outward to networked dependencies in 2.2.

Foundation — what already exists in this repo

  1. Vitest is already wired up. npm test runs vitest run (single pass, CI-friendly exit code); npm run test:watch runs vitest in watch mode for the inner dev loop. No new test runner needs to be introduced for Chapter 3 — the same one scales up.
  2. 13 *.test.ts files already cover the core single-VM path: container-runner.test.ts, container-runtime.test.ts, db.test.ts, db-migration.test.ts, group-queue.test.ts, group-folder.test.ts, routing.test.ts, ipc-auth.test.ts, task-scheduler.test.ts, sender-allowlist.test.ts, remote-control.test.ts, timezone.test.ts, plus channel tests (channels/registry.test.ts, channels/slack.test.ts, channels/wecom.test.ts) and setup/ coverage (environment, platform, register, service). This is real, existing coverage to harden and extend — not a blank slate.
  3. Every hard dependency is already faked at the module boundary. container-runner.test.ts mocks ./config.js, ./logger.js, fs, ./mount-security.js, and ./container-runtime.js via vi.mock(...) — the same "narrow interface + swappable implementation" idea Chapter 3 proposes for IQueue/ILeaseRegistry/IWorkspaceStorage already exists today for Docker, disk, and config.

TIER 0 In-process, mocked — seconds, run on every edit

Faked: Docker (child_process.spawn → fakeProc), wall clock (vi.useFakeTimers()), fs, config.js, logger.js, mount-security.js. Real: container-runner.ts's own spawn-args/parsing/timeout logic runs unmodified; SQLite is a real embedded engine, not a mock.

  1. Docker is faked, not launched. container-runner.test.ts replaces child_process.spawn with vi.mock('child_process', () => ({ spawn: vi.fn(() => fakeProc) })), where fakeProc is an EventEmitter/PassThrough pair standing in for the real container process's stdout/stderr/exit. Tests assert on the args the runner would have passed to docker run and on how it parses the ---NANOCLAW_OUTPUT_START/END--- stdout markers — without ever spawning a container.
  2. The 30-minute idle timeout is tested without waiting 30 minutes. vi.useFakeTimers() plus await vi.advanceTimersByTimeAsync(1830000) fast-forwards the real IDLE_TIMEOUT in milliseconds, so idle-eviction and timeout-reset logic is asserted deterministically in a fraction of a second. This is the exact "virtual clock" idea Chapter 3 generalizes to lease TTL/renewal — it's already proven out here for container idle timeout.
  3. SQLite is real but embedded — no separate database process. db.test.ts calls an exported _initTestDatabase() to get a fresh, isolated database per test run; because SQLite is a library, not a server, "real" and "fast/local" aren't in tension the way they are for Redis/Postgres in the multi-VM design.
  4. fs, config, and logger are all swapped for fakes (existsSync/mkdirSync/writeFileSync/etc. stubbed to no-ops or fixed return values), so no test touches the real filesystem, real env vars, or produces real log noise.

TIER 0 · E2E Full conversation, still fully faked and in-process — the gap this design closes

Faked: everything Tier 0 fakes, plus the chat Channel itself (a test-only registerChannel(...) stand-in instead of Feishu/Slack), and the IPC message files (written directly by the test, not by a real container). Real: the entire orchestrator — processGroupMessages/runAgent/startMessageLoop (or bootstrapApp()) in src/index.ts, src/ipc.ts's flush/task logic, src/router.ts, group-queue.ts, and SQLite session/queue state — none of NanoClaw's own code is mocked here, only its external dependencies.

Everything above tests one link of the chain in isolation. Nothing today drives a full user conversation through the real orchestrator — src/index.ts's processGroupMessages/runAgent/startMessageLoop and src/ipc.ts's task processor are currently 0% covered, not because they're hard to test, but because nothing wires the existing fakes together end-to-end yet. The fix reuses the same building blocks as Tier 0, just assembled once as a full call chain instead of per-module.

  1. A fake Channel, not a fake message. Register a minimal in-memory Channel through the real self-registration mechanism (registerChannel(name, factory) in src/channels/registry.ts) — its sendMessage pushes into an array the test asserts on, and it captures the onMessage callback from ChannelOpts so the test can call it directly to inject synthetic NewMessages. This drives the real orchestrator through its real ingress interface instead of reaching into private functions.
  2. Split main()'s bootstrap from its process-lifecycle concerns. Today main() mixes real wiring (channel registration, queue, the message loop) with process-level side effects (ensureContainerSystemRunning(), SIGTERM/SIGINT handlers, process.exit(0)). Extract an exported bootstrapApp() that returns { channels, queue, shutdown }, with main() reduced to bootstrapApp() + signal wiring + process.exit. Purely additive, same test-only-export convention already used for _setRegisteredGroups and _initTestDatabase.
  3. The same fakeProc from Tier 0, scripted for two turns. Reuse vi.mock('child_process')'s fake process, but script its stdout transcript: turn 1 emits ---NANOCLAW_OUTPUT_START/END--- markers wrapping JSON with a fresh Claude session UUID; turn 2 asserts the same UUID is passed back as resume in the next docker run invocation — proving session continuity through the real Session Manager/SQLite code (_initTestDatabase()), not a mock of it.
  4. Script a mid-conversation IPC task-completion event. Have the fake agent process call processTaskIpc (from src/ipc.ts) with a synthetic completion payload mid-run, and assert the reply is flushed through the fake channel's sendMessage before the container "exits" — the exact question a real user cares about ("did I actually get a reply when the agent finished?"), and the one piece of code with no coverage at all today.
  5. Assertions that matter, in order: turn 1 creates and persists a session UUID; turn 2's docker invocation resumes that same UUID; the fake channel receives exactly the replies a user would see, in order; and after vi.advanceTimersByTimeAsync(IDLE_TIMEOUT) with no further messages, the container is torn down with no dangling queue or lease state.
  6. Still Tier 0. No real Docker, no real network, no real clock — same npm test command, same sub-second speed class. The new file (e.g. src/e2e.test.ts) doesn't add a new feedback loop, it closes the coverage hole in the fastest one.

Simulating a real agent run: two channels, not one

The scenarios above treat one turn as a single result. A real turn is not — the container's actual agent-runner (container/agent-runner/src/index.ts) streams two separate channels while Claude reasons and calls tools, and the fake process needs to script both to be a faithful stand-in.

  1. Channel 1 — intermediate replies, via IPC files, not stdout. Every "thinking" block, tool call, tool-progress ping, and tool-use summary is written by writeVerboseMessage() as a small JSON file ({type:'message', chatJid, text, groupFolder, timestamp}) into /workspace/ipc/messages — mounted from the host's data/ipc/<group>/messages/. The host's flushGroupMessages()/startIpcWatcher() (src/ipc.ts) reads these files in filename (timestamp) order and relays each as its own chat message via sendMessage — this is literally the "🔧 running a command…", "✏️ editing a file…" trail a real user watches scroll by mid-task.
  2. Channel 2 — the final answer, via one stdout marker. Only the SDK's terminal result message triggers writeOutput({status, result, newSessionId}), wrapped in ---NANOCLAW_OUTPUT_START/END--- and parsed by container-runner.ts's onOutput — same mechanism Tier 0's existing tests already use.
  3. Ordering is a real contract, not an accident. flushGroupMessages()'s own doc comment says it exists so "verbose messages arrive in order... before the final result" — i.e. the host explicitly flushes channel 1 before delivering channel 2. An e2e test that only scripts the final marker (as today's Tier 0 tests do) can't catch an ordering regression here; a faithful fake must write both.
  4. The fake needs one new helper: emitVerboseMessage(fakeIpcMessagesDir, text) — writes a timestamped .json file into a temp dir standing in for data/ipc/<group>/messages/, mirroring writeVerboseMessage()'s exact shape. Used alongside the existing emitOutputMarker(fakeProc, output) to script a full turn as an ordered sequence of "verbose event, verbose event, …, final marker."

TIER 1 Real Docker, still local — implemented, Linux-only

Faked: the chat Channel and injected messages (still synthetic, no real Feishu/Slack traffic) — the test calls runContainerAgent() directly. The Claude API call isn't stubbed via a script flag; instead, the claude binary is deliberately left unmounted, so the container fails fast with a clean, well-formed error — proving the marker contract without needing credentials. Real: the actual Docker daemon, the actual built nanoclaw-agent:latest image, real bind mounts built by container-runner.ts's real buildVolumeMounts(), and its real (unmocked) child_process.spawn call — all exercised through a real scratch/throwaway group folder under this repo's own groups/ and data/ directories, cleaned up afterward.

  1. Linux only, by design. Production NanoClaw never runs on Windows — volume-mount and permission semantics differ enough that Tier 1+ tests only run meaningfully on Linux. src/e2e.tier1.test.ts skips itself (with a clear reason) on non-Linux platforms or when no Docker daemon is reachable. On a Windows dev machine, run it from WSL: install a real distro (not the internal docker-desktop VM Docker Desktop uses for itself), install Docker Engine natively inside it (curl -fsSL https://get.docker.com | sh) or enable Docker Desktop's WSL integration, then run wsl -d <distro> -- npm run test:tier1 from the repo checked out on the Linux side (a Windows-mounted /mnt/<drive> path also works, but a native Linux-filesystem copy avoids cross-filesystem bind-mount quirks).
  2. Contract check: does the mock still match reality? src/e2e.tier1.test.ts builds the real image (mirroring container/build.sh, once, if missing) and runs a real docker run against a scratch group folder, asserting the exact ---NANOCLAW_OUTPUT_START/END--- marker contract the Tier 0 fakes assume, plus that the real host directories (group folder, IPC subfolders) actually got created by the real code paths. Run via npm run test:tier1 before merging changes to container-runner.ts or the Dockerfile — it's excluded from the default npm test fast loop (see vitest.config.ts's exclude / the separate vitest.tier1.config.ts) since a real build+run is minutes, not milliseconds.
  3. Found and fixed a real, previously-latent bug this surfaced. container/Dockerfile hardcoded the Playwright-bundled Chromium's crashpad-handler path to a specific revision (chromium-1217); a newer Playwright install produces a different revision directory, so the build silently broke. Fixed by resolving the path dynamically (find /opt/playwright-browsers -path '*/chrome-linux64/chrome_crashpad_handler') instead of hardcoding it — exactly the kind of drift only a real (not mocked) image build catches.
  4. No docker-compose file exists yet for today's single-VM system, and it doesn't need one — there's exactly one Docker daemon and one SQLite file, no multi-service stack to orchestrate locally. This tier is intentionally thin today; it grows into the full docker-compose stack described in 2.2 only once Chapter 3's networked dependencies exist.
  5. Next: same conversation script as Tier 0 · E2E, over a real container. Replay the exact two-turn-plus-idle scenario from Tier 0 · E2E against the real image — same fake Channel and synthetic messages, but a real docker run instead of fakeProc — once a stub for the live SDK call (or a real, sandboxed API key) makes a non-error response feasible in CI.

TIER 2 Live channel + real proxy — minutes, pre-release only

Faked: nothing. Real: live Feishu message delivery/polling, the real OneCLI credential-proxy round trip, the real Claude Agent SDK inside a real container actually deciding which tools to call and executing them.
