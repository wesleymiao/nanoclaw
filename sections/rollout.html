3.2 · Implementation Stages

A staged migration path from today's single-VM NanoClaw to the proposed multi-VM design — each stage ships independently, is testable in isolation, and de-risks the next one. The guiding principle: externalize and validate each piece of shared state while still running on one VM, so the eventual switch to a real multi-VM pool is "just add capacity," not a rearchitecture done under pressure.

0Generalize the group key (no infra change) — Implemented

Refactor group identity everywhere from an implicit Feishu-only shape to the explicit composite key (channel_type, tenant_id, conversation_id): routing resolution, in-process queue partitioning, and the SQLite session/lease lookup. Still one VM, still Feishu-only, still local SQLite/disk — pure refactor with full regression coverage. This is the cheapest possible step and unlocks every later stage without any behavior change a user could notice.

Implemented: new src/group-key.ts introduces the GroupKey type plus parseGroupKey()/formatGroupKey(), deriving the composite key from every channel's existing chatJid convention (prefixed channel:id for Feishu/Slack/WeCom/Telegram/Discord, bare JIDs for WhatsApp), with tenantId defaulted to "default" for today's single-tenant deployment. GroupQueue now partitions its internal state map by the composite key instead of the raw chatJid string. router.ts's findChannel() resolves the owning channel by matching the parsed channelType against each channel's name first, falling back to the original ownsJid() scan for any unrecognized shape. registered_groups gained explicit channel_type/tenant_id/conversation_id columns (migrated and backfilled from existing rows), and getRegisteredGroup() now looks up by those columns instead of the raw jid string. External function signatures and the wire-format chatJid string are unchanged everywhere — channels, IPC, and the DB still speak the same chatJid strings as before. Covered by new group-key.test.ts and router.test.ts, plus the full existing suite (342 tests) with zero regressions.

1Add the Web channel early, as a test harness

Build the new ingress (Container Apps + Front Door + Microsoft Entra External ID) now, while the queue/registry/storage are all still the original in-process/SQLite/local-disk implementations. Because Stage 0 already generalized the group key, Web is just a second producer into whatever the current queue happens to be — no rearchitecture needed to add it this early. The payoff: Web gives a scriptable, rate-limit-free, no-external-dependency way to generate synthetic conversations and load, so Stages 2–7 below can be validated with repeatable scripted traffic instead of waiting on live Feishu conversations (which need real users, real webhook delivery, and are subject to Feishu's own rate limits).

2Externalize the queue (still one VM)

Swap the in-process queue for Azure Service Bus session-enabled queues, but keep exactly one worker process pulling from it on the same single VM. This validates the session-lock semantics (accept, renew, sticky follow-up delivery, idle release) against a real broker's latency and failure modes, with a trivial rollback if anything misbehaves — there's no second worker to coordinate with yet. Drive the validation traffic through the Web channel from Stage 1 rather than needing live Feishu conversations.

3Externalize the session & lease registry (still one VM)

Swap local SQLite for Cosmos DB (or Postgres Flexible Server) TTL leases, still on one VM with one worker. Validates lease acquire/renew/expire behavior against a real networked store before anything depends on it being visible from a second machine. Because only one worker exists, there's no possibility yet of two workers racing for the same lease — that risk is deferred to Stage 6.

4Externalize durable storage (still one VM)

Swap the VM's local disk for an Azure Files (Premium SMB/NFS) or Azure NetApp Files mount, still on one VM. This is the cheapest stage to validate correctness for, since group workspaces, transcripts, and IPC directories can be compared byte-for-byte against the old local-disk behavior with nothing else in the system having changed.

5Reply fan-out via Redis Pub/Sub (still one VM, one replica per channel)

Replace the direct in-process hand-off from worker to socket with a real publish/subscribe round-trip through Azure Cache for Redis, even though only one replica per channel exists to receive it. This proves out the exact mechanism (worker publishes to a conversation_id channel, channel-app subscribes and relays) that becomes mandatory once a second VM exists and the worker can no longer assume it shares a process with the socket owner. Both Feishu and Web channels exercise this identically.

6Cut over to a real multi-VM worker pool

Add a second worker VM (Azure VMSS) pulling from the now-external queue/registry/storage/pub-sub — the riskiest stage, but by now every shared dependency has already been validated independently, so this stage is purely about proving cross-VM coordination: lease hand-off, no double-processing, and explicit chaos tests (kill a worker mid-conversation, confirm a different worker resumes from the shared transcript within the lock's TTL). Web channel's scriptable load is especially useful here for repeatable failover tests. Keep the pool small (2 VMs) until this is solid.

7Add the Autoscaler

Wire up the Azure Monitor autoscale rule watching the queue-depth ÷ pool-capacity custom metric, and validate scale-out/scale-in behavior under synthetic load — including the "never kill a VM with an active lease" scale-in guard. This is deliberately last among the infra stages because autoscaling logic is meaningless (and hard to test convincingly) until a real multi-VM pool exists to scale, and Web channel's scriptable traffic makes it easy to manufacture the sustained load needed to trigger scale-out on demand.

8Hardening & cleanup

Remove any lingering single-tenant/single-VM assumptions and dead code paths, run sustained load and chaos tests across both channels concurrently, and document the operational runbooks (failure handling, manual lease release, scale-in/out tuning) that the earlier stages' ad-hoc validation steps were informally exercising.
